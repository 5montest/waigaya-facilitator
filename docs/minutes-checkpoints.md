# 議事録生成の途中保存と再開

長い会議の分割生成が完了しても、続く統合で失敗すると全分割を再生成する問題を修正した。従来は完成版だけを永続化し、分割結果はジョブ内のメモリにしか保持していなかった。

## 変更

- SQLiteに `minutes_checkpoints` を追加する。既存テーブル・原発言・公開履歴は変更しない。
- 分割結果と各段階の統合結果は、スキーマ・根拠の検証後に保存する。
- 会議IDと、実際のモデル入力・モデル名・指示・スキーマ・成果物種別のハッシュで照合する。発言訂正等で入力が変われば該当処理と依存する統合は再生成する。
- 再試行は最初から処理経路をたどるが、保存済みの処理はAPIを呼ばず読み出す。失敗した統合や未処理部分だけをAPIへ送る。使用量もキャッシュ読出しでは重複計上しない。
- 完成版の承認・公開経路は従来どおり。途中結果を公開版として扱わない。
- 各段階の進捗と再利用件数を保存し、status・議事録画面・ブラウザに表示する。

## 検証

`node --test test/minutes-checkpoints.test.js` は、分割失敗、統合失敗、統合グループ途中の失敗、SQLite再接続、HTTP/会議サーバー再起動後の再試行、入力変更、会議/モデル/途中要約の分離、不正な根拠、保存失敗、キャンセル、状態表示を検証する。APIは模擬し、実OpenAI/Discordには送信しない。

テストの要点は、3分割完了→統合失敗→サーバー/SQLite再起動→再試行でも、分割APIは合計3回のままで増えず、正式議事録が完成すること。

## 導入と制約

1. 実行中の生成がある場合は完了・失敗を確認する。更新のために途中ジョブを終了しない。
2. SQLiteのオンラインバックアップを取得する（稼働中のDB本体ファイルだけをコピーしない）。
3. 更新コードを配置し、Bot/会議サーバーを通常の管理手順で再起動する。テーブル追加は起動時に行う。コマンドの再登録は不要。
4. 再生成時に「保存済み…件を再利用」が表示されることを確認する。

ロールバックは旧コードへの復帰で可能。追加テーブルは旧コードから参照されず、既存の原本と公開履歴はそのまま読める。バックアップ復元では更新後に記録されたデータを失うため、必要な場合のみ停止状態で行う。

チェックポイントは今回の導入後に完了した処理だけが対象。旧プロセスで既に破棄された結果を復元する機能ではない。生成速度の並列化、会議中の増分整理、API障害の詳細分類はこの修正に含めない。統合自体が再び失敗する可能性や、現在の自動再試行回数上限は残る。

実環境への適用・実APIでの長時間会議確認は、このコード変更の自動テストとは別に行う。

## 追加APIを使わない支援AIによる復旧

保存済みの文字起こしを支援AIが直接整理した構造化議事録は、`src/minutes-recovery.js` の `recoverMinutes` でオフライン保存できる。Botと会議サーバーを停止し、DBのバックアップと原本revisionを確認してから行う運用者向けの処理で、Discordの一般操作や公開HTTP APIとしては提供しない。

処理対象は正式版・公開履歴がまだない `finalize_failed` 会議だけ。記録中・一時停止中・終了処理中の別会議があれば拒否する。根拠を検証し、原文・使用量を保ち、人の承認は付けずに正式版を保存する。公開は従来の予約・権限・重複防止を通し、開始通知済みの固定フォーラム自動公開ポリシーに従う。手動復旧であることと追加APIを使わなかったことを版に記録する。途中結果のキャッシュとは別の機能であり、根拠のない本文を自動生成しない。

976件等の大量の障害区間は、Markdownでは種別ごとの件数にまとめる。障害区間は重複するため欠損時間・発言数と同一視しない。元の区間記録はSQLiteから削除しない。

`node --test test/minutes-recovery.test.js test/minutes-checkpoints.test.js test/meeting.test.js` は33件成功。復旧の二重実行、不正な根拠、原本更新、別の実行中会議、原文・使用量・未承認状態の保持、大量注記の表示を模擬検証した。これらのテストで実OpenAI APIは使用していない。
