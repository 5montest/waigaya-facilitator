# ワイガヤの修正案の評価と今回の改善

2026年10月23日のレビュー資料を、稼働コード・SQLiteの記録・自動テストと照合した。短縮IDと途中保存は維持し、音声の取消し条件、議事録の根拠検証、費用の説明を修正した。

## 音声は相槌と割込みを分ける

| 元の案 | 評価 | 今回の対応 |
|---|---|---|
| A：音声割込みの条件を引き上げる | 採用。音量だけを上げると小声の割込みも拾えなくなるため、発声時間で分ける。 | 60msで人の発声を検知して新しい再生を待機させ、同じ発話区間で600msの発声を検知したら再生を止める。300ms未満の短い間は同じ区間として扱う。 |
| B：中断した返答の続きを自動再開する | 今回は見送る。中断後に議論が進むと、古い内容や解決済みの質問を再生する恐れがある。 | 割込み後の返答は自動再開しない。新しい呼びかけで再検討する。 |
| C：再生中は新発言を中断理由にしない | 採用。遅れて確定した文字起こしは、現在の割込みを示すとは限らない。 | 再生許可後の発言追加は音声を止めない。確定発言の訂正、停止、入力消失、モード変更、新しい依頼では取り消す。 |
| D：取消済みTTSをキャッシュする | 今回は見送る。途中まで受信した音声の再利用には再生位置・有効期限・文脈の確認が必要で、別の質問への転用もできない。 | 不要な生成・取消しを減らす処理を先に直す。新たな音声キャッシュは設けない。 |

呼びかけへの返答は、発話が終わって600ms待ってから検討を始める。補足発言が入った場合は最新文脈で一度だけ再検討し、二回目はその時点の入力を使って完成させる。後続の補足をすべて取り込む保証はないが、会話の追加で取消しを繰り返す状態を避けられる。二回目でも根拠の訂正や新しい依頼は取り消し、短い有効期限を維持する。自律的な進行候補は、生成中・待機中に意味のある発言が追加されたら従来どおり失効する。

600msは今回の初期値。実マイクでの相槌・早口・小声・複数人の重なりは、次の実会議で確認する必要がある。名指しだけを停止条件にすると、文字起こしの確定まで停止が遅れるため採用していない。

## 議事録の短縮IDと途中保存は残す

| 既存の修正 | 評価・今回の補強 |
|---|---|
| GLMブリッジへの切替 | 接続経路として維持。Pi上にあるのは中継で、外部のOpenCode Goへ推論を依頼する。費用は未算定とする。 |
| 短縮IDと統合時の再圧縮 | 維持。原本との対応をチェックポイントのキーにも含め、同じ短縮ID・同じ本文でも原発言が違えば結果を混用しない。 |
| 24,000文字の分割・2並列・6分のタイムアウト | 維持。待ち時間と安定性の折衷であり、最適値とまでは確認できていない。 |
| 400文字のスキーマ上限 | 維持。ただしAjvは受信後の検証なので、生成中の肥大化そのものを止める機能ではない。重複・矛盾していた100／250／400文字の指示を整理した。 |
| 検証エラーの上限2回の再試行 | 維持。根拠配列などが欠けた応答も形式エラーとして扱い、使用量は試行ごとに記録する。 |
| SQLiteチェックポイント | 維持。各チャンクに渡した発言だけを根拠として認める。別チャンクに実在するIDを引用した出力も拒否する。 |
| 本文のUUIDと常套句の削減 | 維持。根拠は構造化データに保存し、決定候補・未確認・記録欠損の表示は残す。 |

根拠IDの実在確認に加え、要約が原発言の意味に忠実かどうかも確かめる必要がある。今回の検証は参照先と版の整合性を保証するもので、内容の正しさや参加者全員の合意を証明するものではない。

GLM用に `WAIGAYA_GLM_API_KEY` と `WAIGAYA_GLM_BASE_URL` を追加した。未設定なら従来の `ANTHROPIC_API_KEY`／`ANTHROPIC_BASE_URL` を引き継ぐ。URL末尾の `/v1` の重複も防ぐ。既存の認証ファイルは書き換えていない。会議の開始通知・途中参加者への案内には、議事録生成時に文字起こしをGLM接続先へ送ることも記載した。

## 費用は「確認できた概算」と「不明」を分ける

対象会議 `d7d07ea2-9417-45f6-8114-91b9ca395364` の開始・終了記録の差は約133.09分だった。元資料の「13分」は誤りであり、それを前提にした2時間換算は使わない。

| 種別 | 記録から確認した値 |
|---|---|
| STT | 4,019接続、送信音声の合計6,848.78秒。金額が記録された概算の合計は約$0.4085。972接続は請求額不明。 |
| 呼びかけへの検討 | 44回中36回取消し、8回応答受領。金額が記録された概算の合計は約$0.3920。 |
| 旧議事録生成 | 36件、入力394,824／出力114,558トークン。金額が記録された概算の合計は約$0.9661。 |
| 既知の概算の合計 | 約$1.7666。取消し・失敗・キャッシュ等で費用不明の処理とTTSの請求額を含まない。請求総額ではない。 |
| Botの再生 | 3回とも中断。報告された再生時間は0／1,602／1,880ms。実際の聴取を保証する値ではない。 |

元資料の「STTは$0.07/分、2時間で$4.2」には、計算上の不整合もある。音声費用は会議の経過時間だけでなく、実際に送信した話者別音声の合計と利用モデルで評価する。

Goには契約上の利用枠と、設定による従量課金への切替がある。ローカルブリッジだから無料とは断定できないため、GLMの費用を0として加算する処理を廃止した。OpenAIの議事録呼び出しを置き換えたことと、システム全体の費用がゼロになることを区別する。参考：[OpenCode Go公式説明](https://opencode.ai/v2/docs/console/go)。

## STTの失敗は種類を記録してから対処する

対象会議にはSTT失敗の使用量記録が972件、欠損の可能性を示す区間が976件ある。別の指標であり、失われた発言数や時間には換算できない。旧記録にAPI側のエラー種別がないため、残高不足や通信断などの原因を特定できなかった。

今後は接続失敗、切断、確定待ちのタイムアウト、既知のAPIエラー種別を使用量へ残す。生のエラー本文は保存しない。ローカルSTTへの移行は、原因と認識品質・話者別処理・Piの負荷を確かめてから判断する。

保存済み会議データの確認では、全2,517件のうち対象となる人間の確定発言2,299件を、模擬生成器へ漏れなく渡した。12回の模擬生成で根拠を検証し、同じ入力の再実行は追加生成0回だった。外部APIは呼んでおらず、この検証はGLMの要約品質や実サービスの応答時間を測ったものではない。

不要なimport、使われなくなった状態変数、古い文字数上限、重複した失敗時の費用記録を整理した。既存の会議原本・議事録・公開履歴・チェックポイントは保全している。指示と検証方式を変えたため、旧方式のチェックポイントは今回の生成では再利用しない。再生成する場合は初回の処理が必要になる。

調査は2026年10月23日の稼働リポジトリと読み取り専用のSQLite照合で実施した。自動テストは外部接続を置き換え、Discord・音声・API間の状態遷移を確認する。実会議で最後まで聞けることと、GLMの要約品質は別途確認が必要である。
