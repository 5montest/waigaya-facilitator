# 会議開始直後に記録が止まる不具合の調査

2026年10月17日。保存済みの会議を読み取り専用で調査し、開始処理と復旧処理の競合を再現した。会議本文、参加者ID、認証情報は本書に含めない。

## 原因と影響

対象会議では、開始から約0.2秒後に `recording → paused` が記録され、その後、終了まで文字起こしが0件だった。終了処理はこれを無発言として扱い、`skipped_empty` でフォーラム投稿を省略した。保存履歴にSTT・LLM・Discord送信の障害イベントはなく、投稿を試みた履歴もない。

Botは会議サーバーで記録を開始してからDiscordの通話接続を待ち、接続後に会議を稼働中の変数へ登録していた。その待ち時間に2秒間隔の復旧ワーカーが走ると、開始途中の会議を「Botが不在の会議」と誤認し、一時停止してしまう。通話への接続が成功しても停止状態が残り、音声受信の処理は確定発言を作れない。声による呼びかけも同じ文字起こしを使うため動かない。

模擬Discordの接続待ちの中で実HTTP・WebSocket・SQLiteを通した復旧走査を実行すると、修正前は新規startと明示resumeの両方が `paused` になった。対象会議の状態遷移と一致する不具合を再現できた。イベントには操作者の記録がないため、当日のpauseの発行元そのものをログだけで特定したわけではない。

## 修正

- 接続準備中の会議もセッションIDで稼働中と判定し、復旧ワーカーが停止しないようにした。保護はその会議だけに適用する。
- 接続成功後は通常の会議管理へ引き継ぐ。接続失敗時は保護を解除し、従来どおり記録を停止して復旧・終了できる。
- 文字起こし0件の案内を変更し、実際に参加者が話していなかったと断定しない。話していた場合は音声受信・記録状態の確認を案内する。

開始待ちの復旧走査から、文字起こし・呼びかけへのTTS・正式議事録・フォーラム投稿までの結合テスト、明示resumeの競合テスト、接続失敗後の終了テストを追加した。実行結果は [検証記録](validation.md) を参照。

## データと適用範囲

既存DB・会議・議事録・公開履歴は変更していない。DB移行や設定変更は不要。対象会議には文字起こしがなく、原音声も保存しない仕様のため、このBotの保存データから会話内容を復元できない。

調査時、当該ホストのBotプロセスと会議サーバーは停止していた。今回の調査では実Botの起動・VC参加・DM送信・議事録投稿は行っていない。修正コードの稼働反映と、人のマイクを使う受け入れ確認は別途必要。再起動時は既存DBを保全し、Botとサーバーを重複起動しない。[導入・復旧手順](../discord-setup.md) に従う。

その後、同日のユーザー指示で修正版を適用・再起動した。Discord接続・固定先権限・VC未参加の待機状態を確認した。人の実通話確認は未実施。詳しくは [反映記録](deployment-20261017.md) を参照。
