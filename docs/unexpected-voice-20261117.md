# 意図しない音声応答の調査と対策（2026-11-17）

利用者から「前々回頃に突然発言した」との報告を受け、保存済み会議の呼びかけ履歴、生成要求、音声生成ログと開始設定を調べた。

11月5日の会議では、呼びかけ元の発言は17件。そのうち16件が「今の話をまとめて。」、1件が名前だけだった。16件の依頼文は、STTへ渡していた補助文の「呼びかけ例：ワイガヤ、今の話をまとめて。」と一致する。0.5秒前後の音声区間にもこの全文が現れた。同会議では11回の音声再生許可、5回のTTS生成完了が記録されている。生成完了は、利用者が最後まで聞いたことを示さない。

この会議の生成要求は自律進行ではなく `voice_request` だった。STT補助文の例文を発言と誤認識し、それが直接依頼として動作した可能性が高い。原音声を保存していないため、実際に話した依頼との厳密な区別や、利用者がミュートした瞬間との一致は確認できない。10月22日・29日、11月12日にも同じ依頼文の検出がある。

また、固定運用ではstartのmodeが非表示で、Botとサーバーが環境設定の `on_call` を適用していた。「startだけで議事録のみ」という利用者の期待と異なり、実際は呼びかけ応答が有効だった。

## 対策

- STT補助文から依頼の例文を削除し、固有名詞だけを残す。過去の原本を推測で書き換えない。
- 無指定のstartは、旧環境設定が `on_call` でも議事録のみ。Botと会議APIの両方で適用する。
- 音声参加はstartのmodeで明示選択する。途中変更のmodeコマンドも表示する。どちらも議事録を作る。
- 議事録のみでは回答・TTSの既存禁止に加え、Discord再生側でもモードを検査する。モード変更時には待機中の呼びかけを取り消す。
- statusにモード名とAI音声のON/OFFを常時表示する。
- サーバーミュート・Bot自身のミュートを検知したらAIだけ停止し、解除だけでは再開しない。個人側のミュートはBotから検知できないため、全員に対して止めるにはmodeまたはquietを使う。

明示した音声参加中も、STTの誤認識を完全に排除したとはいえない。今回、実音声による再現や有料API検証は行っていない。議事録のみで音声が出ないことと、切替・遅着音声の拒否を模擬Discord・HTTP・SQLiteの結合テストで検証する。

操作は [簡易説明書](quick-start.md) を参照。DBスキーマの変更はない。反映時は会議がないことを確認し、DB・既存設定をバックアップしてから更新、コマンド再登録、サービス再起動を行う。復旧する場合はサービス停止後に変更前の `f8a44e5` へ戻す。ただし旧版はstartで音声参加するため、復旧時も環境設定を `minutes` に保つ。

検証結果：`flock --wait 120 /immich/media/agent-hub-data/browser-work.lock npm test -- --test-concurrency=2` は330件成功、失敗0、skip 0（約92.6秒）。ブラウザ・模擬Discord・HTTP・SQLiteを含む。`git diff --check` と差分の認証情報パターン検査も実施する。有料OpenAI API呼び出しは0回。
